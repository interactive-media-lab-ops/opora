# Завдання бекенду від UI (етап 8, зрізи 1–3)

Файл для передачі бекенд-розробнику. Оновлено **2026-11-02** (після зрізу 4). Цей файл — робочий список: що зробити, навіщо, яку форму API очікує фронтенд і як перевірити. Розподіл ролей — DD-43 (4A): UI — Макс (`frontend/src/index.css`, `components/*`, розмітка сторінок, маршрути), логіка й API — бекенд-розробник; у `backend/` з боку UI змін немає.

Правила, які вже дотримані на боці UI і які варто не зламати на боці API:
- UI не підробляє поведінку: доки поля чи ендпоінту немає, функція схована або кнопка недоступна з причиною. Кожне місце позначено в коді `// TODO(backend-requests: BR-n)` — `grep -rn "backend-requests" frontend/src`.
- Усі виклики моделей — лише через NearAI у бойовій конфігурації (X-26, BR-11). Нових AI-викликів з UI немає.
- Демо-дані — лише вигадані (DD-03). Ніяких реальних людей у seed.

Пріоритети: **P1** — блокує вже готовий UI (поле або ендпоінт потрібні, щоб екран працював за дизайном); **P2** — рішення ухвалено, UI підготовлено або зробиться за день; **P3** — конфігурація, дані для перевірки, пізніші рішення.

## P1 — блокує готовий UI

### BR-14 · Ім’я та посада кандидата для рекомендатора
**Навіщо.** Мок R3 / R4 (власник 02.11, рішення 1A — пріоритет): на кроці ролі «Людина: **ПІБ**, посада», у питаннях «Людина: **ПІБ** · ваша роль: …». На вступі R1 імені немає (D-10). Імʼя самого рекомендатора не запитуємо (D-10, D-17).
**Що зробити.** `GET /recommend/:token` → додати `candidate: { name: string, post: string | null }`. Якщо принципово не віддавати імʼя до кроку «Почати» — окремий `GET /recommend/:token/candidate`, який UI викличе після R1 (тоді повідомте, і я переключу запит).
**Фронтенд.** `frontend/src/api/types.ts` (`PublicRecommendation.candidate?`), `frontend/src/pages/recommend/Recommend.tsx` — рядки з’являються автоматично, щойно поле є.
**Перевірка.** Відкрити `/r/<token>` → «Почати» → на кроці ролі видно ПІБ і посаду; без поля — рядків немає, помилок немає.

### BR-5 · База HR: усі кандидати, рубіж етапів «N / M», сортування
**Навіщо.** 78A (DD-44), D-22 / D-60: HR бачить усіх кандидатів із прогресом етапів; сортування за іменем, повнотою профілю, датою оновлення; кольору за повнотою немає.
**Що зробити.** `GET /hr/candidates`: (1) віддавати всіх кандидатів, не лише тих, хто надіслав усі етапи; (2) у рядку поле `stages: [{ key, title, status: "NOT_STARTED" | "IN_PROGRESS" | "SUBMITTED" }]` (як `StageInfo` кандидата) і `updated_at`; (3) `?sort=name|completeness|updated&dir=asc|desc` замість `date|score` (старі значення можна лишити як синоніми на перехід).
**Відкрито.** Визначення «повноти профілю» для `completeness` — Q-51 (Роман); сортування за замовчуванням — `updated desc` (власник 02.11, 94A).
**Фронтенд.** `frontend/src/components/CandidateList.tsx` (`TODO(backend-requests: BR-5)`): зараз сортування за ПІБ — на клієнті, «Подано ↓» і «Бал ↓» — сервером; колонки «Етапи N / M» немає, з’явиться з полем `stages`.
**Перевірка.** У базі є кандидат з одним надісланим етапом і рубежем «1 / 4»; сортування за трьома ключами в обидва боки.

### BR-6 · Нотатки HR — свої в кожного HR, з автором
